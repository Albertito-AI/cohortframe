# Architecture and agent contract

## Components

- `models.py`: strict JSON parsing, manifest constraints, typed errors and canonical content.
- `core.py`: canonical SQLite project/job state, revision checks, snapshot creation, idempotency, transitions and recovery.
- `render.py`: bounded local scene rendering, explicit FFmpeg subprocess invocation, media validation and artifact provenance.
- `font.py`: bundled project-authored bitmap glyphs, without a runtime font download.
- `cli.py`: one JSON command interface and an original procedural demonstration.

The application has no HTTP listener or cloud SDK. Its caller already has local operating-system access. SQLite is the authoritative record; job input snapshots are copied before execution. The project dictionary returned to an agent is a representation, not a capability grant or a security token.

## Consistency

Creating a project establishes its first revision. Updating it requires the expected revision. A conflicting edit fails rather than overwriting another actor's newer work.

A job's idempotency key is scoped to its project. Repeating an identical submission identifies the existing job; reusing the key for a different requested revision produces a conflict. The interface cannot guarantee provider billing semantics because no live provider is implemented.

Snapshots preserve the manifest and imported audio used for the job. Later project edits or changes to the original audio must not change those inputs. Artifact hashes describe produced bytes; they are not publisher signatures or proof of semantic correctness.

## Work and recovery

Jobs are explicitly queued and run. State includes queued, running, succeeded, failed, cancellation requested, cancelled and interrupted. A worker must claim a job atomically; concurrent execution must not silently duplicate it. Terminal successful jobs are inspected rather than regenerated by an ordinary repeated run.

Cancellation requests are observed during rendering. A request is not itself evidence that execution has stopped. Recovery should identify abandoned work without taking a job away from a live worker. Retry remains an explicit action after a failed or interrupted attempt and uses the stored inputs.

No perpetual scheduler or cloud orchestration exists in v0.1. The operating process must remain available to finish its work. Recovery behaviour is tested as a local process property, not a distributed-service guarantee.

Abandoned-worker recovery uses POSIX process liveness and, on Linux, process-start identity to avoid confusing reused identifiers. Non-POSIX recovery conservatively leaves recorded workers alone; automatic abandoned-worker recovery on Windows is not supported in v0.1. Cross-platform process ownership needs a separately verified implementation.

## Stable extension points

Future provider adapters should accept typed generation requests, bind authorization to an approved provider/destination, meter resources, preserve provider job identifiers and expose ambiguous outcomes. Their credentials belong outside model prompts and project files. Billing, secret custody and durable remote reconciliation require new reviewed implementations.

Future UI and agent protocols should use the same project and job operations. An interface version change needs compatibility fixtures or an explicit migration. No school enrolment is required for an ordinary authorised product client.
